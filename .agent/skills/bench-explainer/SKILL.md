# 讲解一个评测 bench

## 这份指引的性质

本指引只是引导，不是固定模板。下面的部分、维度、问题和选项都是例子，用来提示你该看什么。各部分里的「以下是例子」都是这个意思。

处理对不上的情况，按一条规则：
- 跟这个 bench 无关的维度，不写。
- 有关但套不进任何选项的，按实际情况描述，不要硬塞。
- 本指引没列出、但用户应该知道或建议知道的内容，自己加上。

部分可以合并、拆分或调整顺序，以实际情况为准。

## 先找资料

讲解之前，先把这个 bench 的资料找全。以下是常见来源的例子，不必每种都有，也可能有别的来源：
- 论文：最早的设计说明。论文往往偏旧，后续版本的改动不一定写进去。
- 官方博客或发布页：常常写新版本的改动和设计理由。
- GitHub 仓库：评测代码、配置、提示模板、判分脚本。设置以这里为准。
- Hugging Face 数据集页：题目格式、数量、划分、许可证，可以直接看几道样题。
- 官方榜单和方法页：当前用的版本、设置和分数。
- 第三方榜单和厂商发布卡：例如 Artificial Analysis、Epoch、各家模型发布卡。它们的设置可能和原版不同。
- 他人的解读：技术博客、复现报告、论坛和社交媒体上的讨论，常常指出缺陷和坑。
- 版本演进：changelog、仓库的 release 和 issue、新版本论文。理清有哪些版本，每个版本改了什么。
- 其他：任何与这个 bench 相关的在线资料。

找不到某类资料就跳过，在讲解中说明哪些资料没找到。

## 开始写之前

先判断自己在什么环境里，再决定能做到哪一步。以下是例子：
- 在用户自己的电脑上：大规模下载、拉取镜像、运行容器，或其他占空间、有风险的操作，先问用户是否允许。
- 有自己的云电脑：直接做，可以持续深挖，包括进入镜像查看环境。
- 只能聊天、不能执行：只依据网上资料讲解，并说明哪些内容无法验证。
- 其他环境：按实际能力判断。

先满足下面的底线，再开始写。以下是例子，按 bench 的实际情况调整：
- 有公开数据集，就实际加载看一遍，例如题量、划分、字段、重复项，或其他。不要只引用 README 里的数字。
- 每种主要的题型、领域或交互形态，至少看一道题，再加上边界题和例外。不要用一道题代表整个集合。
- 从题目到最终分数，至少在代码里完整跟一遍，例如加载、变换、模型实际看到的输入、工具执行、判分、合成，或其他环节。

做不到的部分，记下原因，例如没公开、工具读不到、用户没允许、还没来得及看，或其他原因。

## 讲解的规则

这些规则的目的是让讲解可信、好读。

1. 用和用户相同的语言，用平实的说法。一句话只讲一件事。术语第一次出现时，用一句话解释。
2. 先讲一道真实的题，从输入到最终分数完整走一遍。然后再按部分展开。
3. 每个结论注明来源：论文、官方代码、官方榜单，或者你的推测。推测要明确写「推测」。
4. 查不到的写「没查到」。不要编数字、编设置、编来源。
5. 优先查官方仓库的评测代码和配置。论文写法和代码不一致时，两者都写出来，并以代码为准说明差异。
6. 能用小算例说明的地方，用小算例，例如三道题、两次采样、一个判官。
7. 先说明讲的是哪个版本。bench 有多个版本时，分开讲，不要混在一起。
8. 分清 bench 原版和榜单上的变体。同一个名字在不同榜单上的设置可能不同，要指出差异。
9. 新旧资料冲突时，以最新的为准，旧说法注明已过时。
10. 控制篇幅。开头的概括要能单独读懂，细节放在后面。

## 讲解的部分

以下各部分的顺序，大致对应一道题从输入到分数的流程。

### 1. 基本信息

以下是例子，按需取舍：
- 发布方、发布时间、当前版本、题目数量。
- 想测的能力：知识、推理、数学、代码、agent 操作、写作、安全、多语言，或其他。
- 谁在用它：模型发布卡、第三方榜单、研究论文，或其他。

### 2. 题目和输入

以下是例子：
- 模态：纯文本、图像、音频、视频、多种混合，或其他。
- 题目来源：人工出题、取自真实数据、模型生成后人工筛选，或其他。
- 题型：选择、填空、开放回答、交付物（代码、文件、网页）、多步任务，或其他。
- 防泄漏：公开集与隐藏集、定期换题、按时间切分，或其他，或没有。

### 3. Rollout：从题目到输出

Rollout 指被测模型拿到题目以后，一直到产出最终输出的全过程。所有 bench 都有 rollout，形式差别很大。

讲清这个 bench 的 rollout 是什么样的。各家 bench 的 rollout 差别最大，下面的维度尤其只是常见例子：无关的不写，套不进的照实描述，没列出但重要的自己加。

harness 指负责把题目交给模型、驱动交互、收集输出的那套东西。它可以是一个评测框架，可以是一个 agent 框架，可以是一段自写的循环脚本，也可以只是一次 API 调用。

以下是例子：

- 交互形态：只读概率，不生成；单轮直接输出答案；单轮内多步调用工具；多轮对话；需要模拟用户或其他角色参与；提交后拿到反馈再修改；在环境里持续行动直到任务结束；或其他。
- 谁来驱动：没有 agent loop，一次调用直接出结果；现成的 agent 框架，例如 OpenHands；bench 自带的循环；厂商自己的 agent；人类在环；或其他。
- 模型怎么接入：调用 API 还是加载权重；是否用 chat template；推理或思考模式是否打开；工具调用走原生 function calling 还是文本格式解析；或其他。
- 能拿到什么、不能拿到什么：能否联网和搜索；能否看到测试用例或标准答案；工具权限多大；上下文里预先给了哪些文档；或其他。
- 需要什么基础设施：代码沙箱、终端、浏览器或 GUI；MCP 服务器或其他工具；外部服务和 API key；自部署的模型；GPU 等算力；辅助的模拟器、数据库或文件；或其他。
- 环境怎么组成（主要针对 agent 类 bench）：一题一个容器或 pod；需要虚拟机或 KVM，例如完整桌面系统；主容器加 sidecar，例如数据库、模拟网站、模拟用户；一题多个互相通信的容器；verifier 单独运行在另一个容器里，或需要多个 verifier；或其他。
- 初始状态和隔离：每题从什么状态开始；题与题之间是否重置；随机种子是否固定；并发运行时是否互相干扰；或其他。
- harness 替模型做了什么：提示模板、系统提示、few-shot 示例；答案抽取和格式修复；出错重试和超时处理；上下文截断或压缩；保存完整轨迹供判分使用；或其他。
- 采样和终止：温度、采样次数 k、思考预算；最大步数、时间上限或 token 上限；终止由模型决定还是由环境判定；或其他。
- 故障怎么算：环境崩溃、超时、API 报错时，记 0 分、重跑还是剔除这道题；或其他。
- 能否复现：harness 和环境是否公开，版本是否固定，自己能否跑起来，大概要多少成本。

同一个 bench 换一个 harness 或换一套设置，分数可能差很多。指出这个 bench 上影响最大的设置。

### 4. 如何出分

讲清这个 bench 从判定到最终数字的计算过程。出分规则因 bench 而异，下面的问题和例子都不是固定答案。

先说明一道题由谁来判、和什么比。以下是例子：
- 谁来判：程序比对、运行测试或检查最终状态、模型判官、人工、奖励模型，或其他。
- 和什么比：标准答案、细则清单、参考输出、另一个模型的输出、人类基线，或其他。
- 有判官时：判官是哪个模型，是否给参考答案，判几次，判官之间怎么合。
- 程序和模型一起判时：最终的对错由谁决定。

然后按下面的问题逐个说明，无关的问题跳过：
1. 最小的计分单位是什么？例如一条细则、一道题、一组配对题、一局。
2. 一个单位怎么得分？例如对错、部分分、带正负分值、连续值。
3. 有没有门槛或一票否决？例如某条不过整题记 0，拒答记 0。
4. 多个单位怎么组合成上一层的分数？例如相加、取最小、要求同时成立、先平均再截断或先截断再平均。
5. 多次采样怎么合？例如平均、pass@k、maj@k、选择器挑一个。注意 maj@k 是先对答案投票，再判对错。
6. 有没有加权、分组、截断或换算？例如换算成人类耗时或 rating。
7. 最终报告的数字是什么？

以下是一些不常见的出分规则，只用来提醒你出分可能有这些弯绕。不要把 bench 往这些例子上套：
- 正向题和反向题配对，两道都对才得分。
- 细则带负分，总分扣到负数后截断成 0。
- 先截断再平均，和先平均再截断，结果不同。
- 拒答单独计分，或拒答直接记 0。
- 分数不超过已通过关卡的权重占比。

两条必须做到的要求：
- 从官方代码或方法页中，把出分规则写成一条公式或几行伪代码，并注明出处。
- 用三到五道题的小例子，手算一遍出分全过程，算出最终数字。

### 5. 多个模型之间怎么比

讲清这个 bench 上不同模型的分数怎么比较、能不能比较。以下是例子，按实际情况取舍：
- 比较方式：各自得一个绝对分再比高低；两两对战后用 Elo 或 Bradley-Terry 拟合；按名次或胜率合并；或其他。
- 分数是否依赖其他参评模型：新模型加入后，老模型的分数或名次会不会变。用 Elo 或 Bradley-Terry 时，锚点是谁，钉在多少分。
- 设置是否一致：各家是不是在同一个框架、同样的提示、采样次数和思考预算下跑的。自报分数和第三方复测分数要分开说。
- 差多少才算有区别：置信区间或标准误有多大，平局怎么算。
- 成本和速度：是否一起报告，是否画成成本和分数的前沿图。
- 版本：不同版本、不同时间的榜单能不能直接对比。

用一个两三个模型的小例子说明比较过程。如果这个 bench 只给单个模型打分、不涉及比较方法，就简短说明怎样比较才公平。

### 6. 分数怎么读

以下是例子：
- 满分和随机基线是多少，人类水平是多少。
- 常见问题：饱和、题目泄漏、判官偏好、版本变化后不可比，或其他。

### 7. 这个 bench 特别在哪（必须写）

本部分没有固定维度，是留给这个 bench 自己的。
找出 3 到 5 个这个 bench 和普通 bench 不一样、值得用户关注的点。
可以从下面的方向想，这些也只是例子：
- 设计上的非常规选择，以及它为什么这样选。
- 某个设置一改，分数就会大变。
- 容易被误读的数字或名字。
- 和同类 bench 相比，多测了什么或少测了什么。
- 争议、已知缺陷或后续修订。
每个点写清楚：是什么，为什么值得关注，来源是什么。

## 输出格式

1. 开头用两三句话概括：这个 bench 测什么，分数怎么来，读分数时最该注意什么。
2. 一道真实题从输入到分数的完整流程（见讲解规则第 2 条）。
3. 按上面的部分逐一讲解。
4. 第 7 部分的 3 到 5 个关注点。
5. 最后列出用到的来源链接。
6. 列出已查和未查的范围：实际读过或运行过的内容，还没验证的内容和原因。
7. 从没验证或值得深挖的内容里，给用户三个接下来可以继续看的方向，例如没细看的子集、没跑过的代码、没核对的榜单变体，或其他方向。每个方向写一句为什么值得看。
8. 用户还没说要文档时，最后问一句是否需要整理成完整的介绍文档。用户同意后，再问清格式和存放位置。

需要时，可以用一张简单的流程图或表格说明结构。
